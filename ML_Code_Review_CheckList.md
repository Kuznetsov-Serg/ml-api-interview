# 📋 ML Code Review Checklist (v2.0)

Чек-лист для ревью кода от Data Scientists перед передачей в Production.
Цель: обеспечить надежность, производительность, безопасность и наблюдаемость ML-сервисов.

> 💡 **Правило "Двух минут":** если код не проходит более 3-х пунктов из блоков 3, 4 или 6 —
> он автоматически отправляется на доработку без углубленного ревью алгоритмической части.

---

## 🏗️ 1. Архитектура и структура кода (5 пунктов)

- [ ] **Разделение ответственности:** код обучения (training) и инференса (inference) разделены.
      Notebooks — только для EDA/прототипирования, финальная логика вынесена в `.py` модули.
- [ ] **Отсутствие глобальных переменных:** состояние модели и конфигурации передаются через
      аргументы функций или Dependency Injection, а не через `global`.
- [ ] **Конфигурация:** все гиперпараметры, пути, URL вынесены в `.env` / `config.yaml` /
      Pydantic Settings, а не захардкожены.
- [ ] **Типизация:** используются `type hints` + Pydantic-модели для валидации входных/выходных
      данных API.
- [ ] **Абстракции для моделей:** единый интерфейс `BaseModel` (или Protocol) для всех моделей,
      Registry-паттерн для регистрации — это позволяет быстро "обернуть" новую модель в API.

---

## ⚡ 2. Производительность и оптимизация (5 пунктов)

- [ ] **Векторизация (pandas/numpy):** отсутствуют циклы `for`, `iterrows()`, `itertuples()`
      для построчных операций. Используются `np.where`, `df.apply` — только как крайняя мера.
      *(Кейс: notebook_ml_1)*
- [ ] **Chain operations для агрегаций:** вместо цепочки промежуточных DataFrame — один `agg()`
      с несколькими функциями или `groupby().agg({...})`.
      *(Кейс: notebook_ml_2)*
- [ ] **Lazy Loading:** тяжелые объекты (модели, эмбеддинги, большие словари) загружаются
      один раз при старте приложения (через `lifespan` в FastAPI), а не при каждом запросе.
      *(Кейс: notebook_ml_1, notebook_ml_3)*
- [ ] **Batching:** взаимодействие с внешними сервисами (LLM API, БД) выполняется батчами,
      а не по одному элементу. Используется SSE для streaming-ответов.
      *(Кейс: notebook_ml_3)*
- [ ] **Управление памятью:** отсутствуют утечки (накопление списков в цикле, лишние `.copy()`),
      используются генераторы для больших файлов, `chunksize` при чтении CSV/записи в БД.

---

## 🛡️ 3. Надежность и обработка ошибок (5 пунктов)

- [ ] **Graceful Degradation:** сервис не падает при сбое зависимостей (Redis недоступен →
      запрос идёт напрямую в БД; модель не загрузилась → 503 с понятным телом).
- [ ] **Retry + Circuit Breaker:** для внешних сетевых вызовов настроены повторные попытки
      с экспоненциальной задержкой и предохранители (Tenacity / pybreaker).
- [ ] **Валидация на границах:** на API endpoints данные строго валидируются по типу, диапазону
      и размеру (защита от OOM и инъекций).
- [ ] **Structured Logging:** JSON-логи с `request_id` для трассировки. Логируются не только
      ошибки, но и бизнес-метрики (время инференса, размер батча, cache hit/miss).
- [ ] **RFC 7807 Problem Details:** единый формат ошибок с `type`, `title`, `status`, `detail`,
      `instance` — клиенту понятно, что произошло.

---

## 🔐 4. Безопасность и данные (5 пунктов)

- [ ] **Отсутствие секретов в коде:** API-ключи, пароли, токены не закоммичены (проверено через
      `detect-secrets` / `trufflehog` в pre-commit).
- [ ] **Детерминированность обучения:** зафиксированы `random_state` / `seed` для
      воспроизводимости результатов.
- [ ] **Безопасная сериализация:** предпочтительны ONNX / Safetensors / JSON вместо `pickle`.
      Если используется `pickle` — источник файлов строго контролируется (подпись, hash).
- [ ] **Rate Limiting + CORS:** настроены на уровне middleware (slowapi / nginx),
      whitelist доменов для CORS.
- [ ] **Аутентификация:** JWT / API Key для внешних клиентов, RBAC для внутренних.

---

## 🧪 5. Тестируемость (5 пунктов)

- [ ] **Unit-тесты:** критическая бизнес-логика и функции препроцессинга покрыты тестами
      (pytest), внешние зависимости мокаются.
- [ ] **Integration-тесты:** API endpoints тестируются через `TestClient` с реальной БД/Redis
      (через testcontainers).
- [ ] **Coverage > 80%:** порог покрытия зафиксирован в CI.
- [ ] **Контракты данных:** схема входных/выходных данных инференса задокументирована
      (OpenAPI) и совпадает с ожиданиями клиентских систем.
- [ ] **Test data management:** тестовые данные генерируются скриптами (`faker`, `hypothesis`),
      не хранятся в репозитории.

---

## 🚀 6. Production Readiness (5 пунктов)

- [ ] **Контейнеризация:** корректный `Dockerfile` (multi-stage build, non-root user,
      `.dockerignore`, layer caching).
- [ ] **Kubernetes-ready:** liveness/readiness probes, HPA, resource limits/requests,
      graceful shutdown.
- [ ] **Мониторинг:** кастомные Prometheus-метрики (latency модели, cache hit rate, 5xx errors),
      Grafana-дашборд, алерты.
- [ ] **CI/CD пайплайн:** lint → test → build → push → deploy, автоматический rollback
      при росте ошибок.
- [ ] **Data/Model Drift мониторинг:** отслеживание деградации модели в production
      (Evidently AI / NannyML / кастомные метрики).

---

## 🎯 Быстрый чек перед отправкой на ревью

1. Код проходит `ruff check`, `black`, `mypy` без ошибок?
2. `pre-commit run --all-files` чист?
3. `pytest --cov=app` показывает coverage > 80%?
4. `docker-compose up` поднимает сервис без ошибок?
5. `/health` возвращает 200, `/metrics` отдаёт Prometheus-формат?

Если на все 5 вопросов ответ "Да" — код готов к углубленному ревью.
