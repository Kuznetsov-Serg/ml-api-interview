## 📋 ML Code Review Checklist

Этот чек-лист используется для ревью кода, передаваемого от Data Scientists в Production. Цель: обеспечить надежность, производительность и поддерживаемость ML-сервисов.

### 🏗️ 1. Архитектура и структура кода
- [ ] **Разделение ответственности:** Код обучения (training) и код инференса (inference) разделены. Ноутбуки используются только для EDA и прототипирования, финальная логика вынесена в `.py` модули.
- [ ] **Отсутствие глобальных переменных:** Состояние модели и конфигурации передается через аргументы функций или классы (Dependency Injection), а не через `global`.
- [ ] **Конфигурация:** Все гиперпараметры, пути к файлам и URL вынесены в конфиги (`.env`, `config.yaml` или Pydantic Settings), а не захардкожены в коде.
- [ ] **Типизация:** Используются type hints (`typing`) и Pydantic-модели для валидации входных/выходных данных API.

### ⚡ 2. Производительность и оптимизация
- [ ] **Векторизация:** В Pandas/NumPy коде отсутствуют циклы `for` и `iterrows()`/`itertuples()` для построчных операций. Используются векторизованные функции (`np.where`, `apply` только как крайняя мера).
- [ ] **Lazy Loading:** Тяжелые объекты (ML-модели, эмбеддинги, большие словари) загружаются один раз при старте приложения (например, через `lifespan` в FastAPI), а не при каждом запросе.
- [ ] **Batching:** Взаимодействие с внешними сервисами (LLM API, базы данных) выполняется батчами, а не по одному элементу за раз.
- [ ] **Управление памятью:** Отсутствуют утечки памяти (например, накопление больших списков в цикле без очистки, использование `.copy()` там, где это не нужно).

### 🛡️ 3. Надежность и обработка ошибок
- [ ] **Graceful Degradation:** Сервис не падает полностью при сбое зависимостей (например, если Redis недоступен, запрос идет напрямую в БД; если модель не загрузилась, возвращается понятная 503 ошибка).
- [ ] **Retry и Circuit Breaker:** Для внешних сетевых вызовов (БД, внешние API) настроены повторные попытки (retry) с экспоненциальной задержкой и предохранители (circuit breaker).
- [ ] **Валидация входных данных:** На границах системы (API endpoints) данные строго валидируются на тип, диапазон значений и размер (защита от OOM и инъекций).
- [ ] **Логирование:** Используются структурированные логи (JSON) с `request_id` для трассировки. Логируются не только ошибки, но и ключевые бизнес-метрики (время инференса, размер батча).

### 🔐 4. Безопасность и данные
- [ ] **Отсутствие секретов в коде:** API-ключи, пароли и токены не закоммичены в репозиторий (проверено через `detect-secrets` или `trufflehog`).
- [ ] **Детерминированность:** В коде обучения зафиксированы `random_state` / `seed` для воспроизводимости результатов.
- [ ] **Безопасная сериализация:** Для сохранения моделей предпочтительны безопасные форматы (ONNX, Safetensors, JSON) вместо `pickle`, если это возможно. Если используется `pickle`, источник файлов строго контролируется.

### 🧪 5. Тестируемость и Production Readiness
- [ ] **Unit-тесты:** Критическая бизнес-логика и функции препроцессинга покрыты тестами (pytest). Моки используются для внешних зависимостей.
- [ ] **Контракты данных:** Схема входных и выходных данных инференса задокументирована и совпадает с ожиданиями клиентских систем.
- [ ] **Контейнеризация:** Приложение имеет корректный `Dockerfile` (multi-stage build, non-root user, `.dockerignore`).
- [ ] **Мониторинг:** Добавлены кастомные метрики (Prometheus) для ключевых операций (latency модели, hit rate кэша, количество ошибок 5xx).

> 💡 **Правило "Двух минут":** Если код не проходит более 3-х пунктов из разделов 3 или 4, он автоматически отправляется на доработку без углубленного ревью алгоритмической части.
